# Универсальная структура: как делают другие, и как сделать удобно у нас

**Статус:** предложение, на обсуждении
**Дата:** 20.09.2026
**Связано:** [спека этапа 1](../superpowers/specs/2026-09-19-triage-workflow-and-ai-design.md), [исследование процесса](2026-09-19-findings-workflow-research.md)

## 1. Как устроено у других

| Продукт | Модель | Что подсмотреть |
|---|---|---|
| **DefectDojo** | Жёсткая лестница Product Type → Product → Engagement → Test → Finding | **auto_create_context**: CI передаёт имена, платформа сама создаёт всю цепочку. CI не делает «найди или создай» ([документация](https://docs.defectdojo.com/en/connecting_your_tools/import_scan_files/api_pipeline_modelling/), [DeepWiki](https://deepwiki.com/DefectDojo/django-DefectDojo/5.3-import-and-reimport-endpoints)) |
| **OWASP Dependency-Track** | Проекты с родителем и ребёнком, любая вложенность + свободные теги | Ровно наша модель. Дети **наследуют настройки** родителя (политики, уведомления). В версии 4.13 добавили **collection-проекты**: родитель без своих компонентов, только агрегирует метрики детей ([документация](https://docs.dependencytrack.org/usage/collection-projects/), [концепция](https://dependencytrack.github.io/docs/next/concepts/projects/), [зачем это](https://www.dependencytrack.com/the-value-of-project-collections-in-owasp-dependency-track/)) |
| **Backstage** (Spotify) | Каталог сущностей: Component, System, Domain, Group + связи `ownedBy`, `partOf` | **Описание лежит в репозитории** (`catalog-info.yaml`) и подхватывается автоматически. Владелец — обязательная связь, на ней держится ответственность ([модель](https://backstage.io/docs/features/software-catalog/system-model/), [Roadie](https://roadie.io/blog/understanding-the-backstage-system-model/)) |
| **Snyk** | Tenant → Group → Organization → Target → Project + теги | Структуру советуют строить **по правам доступа**, а не «как красиво». Дальше — политики, потом отчётность ([docs](https://docs.snyk.io/snyk-platform-administration/snyk-projects), [training](https://learn.snyk.io/lesson/groups-and-organizations/)) |
| **GitLab** | Подгруппы до 20 уровней, наследование прав вниз | Глубокая вложенность + много детей = **тормоза и таймауты** на правах и дашбордах ([docs](https://docs.gitlab.com/user/group/subgroups/)) |
| **Faraday** | Плоские workspace | Простота, но без агрегации по портфелю |

**Общий вывод индустрии:** побеждает связка **дерево + теги**. Дерево даёт «место» и наследование настроек, теги — вторую координату (среда, критичность, команда), потому что одной иерархией всё не описать. Типичные грабли тегов: расползание значений и пустые теги без владельца ([Device42](https://www.device42.com/vulnerability-management-best-practices/asset-tagging-in-vulnerability-scanner/), [обзор таксономий](https://aetopia.com/blog/dam-taxonomy-a-practical-guide.html)).

## 2. Что менять у нас

Модель Entity оставляем. Добавляем пять вещей.

### 2.1. Путь как адрес (`path`)
У каждого узла — слаг (`backend-api`), у дерева — полный путь `fintech/payments/backend-api`, уникальный. Зачем:
- CI обращается по пути, ему не нужно знать UUID;
- путь читается в логах, ссылках и в API;
- полный путь хранится в поле `path_cache` (materialized path) — по нему дешёво считать поддерево, без рекурсивных запросов. Это заранее снимает проблему производительности, на которую жалуются в GitLab.

UUID остаётся основным идентификатором: переименование не ломает ссылки.

### 2.2. Автосоздание из CI (как auto_create_context)
```
POST /api/v1/imports   (multipart)
  file=@semgrep.sarif
  project_path=fintech/payments/backend-api
  auto_create=true
  branch=main  commit_sha=abc123  scan_scope=api:latest
```
Недостающие узлы создаются сами. В GitLab это одна переменная `CI_PROJECT_PATH`, то есть структура платформы зеркалит структуру репозиториев без ручной работы. Автосоздание включается настройкой и правом `entity:write` у токена.

### 2.3. Теги — вторая координата
Свободные метки `env:prod`, `team:payments`, `criticality:high`. По ним фильтры, отчёты и области действия политик SLA. От расползания: справочник разрешённых ключей в настройках и подсказки в UI.

### 2.4. Узел знает свой репозиторий
`repo_url` (+ тип и подпапка для монорепо) — он же ключ от задвоения: один репозиторий = один узел. Плюс из этого собираются ссылки на строку кода (уже сделано в этапе 1).

### 2.5. Настройки в репозитории (по желанию, позже)
Как `catalog-info.yaml` в Backstage: файл `.secretvuln.yml` в репозитории с владельцем, тегами и основной веткой. CI прикладывает его к импорту, платформа применяет. Настройки живут рядом с кодом и не разъезжаются.

### Чего НЕ делаем
- **Типов узлов не вводим.** Гибкость — наше отличие от DefectDojo.
- **Отдельный флаг «collection»** (как в Dependency-Track) не нужен: у нас узел и так может одновременно содержать детей и принимать отчёты, а агрегаты считаются для любого узла.
- **Жёсткого ограничения глубины нет,** но в UI предупреждаем после ~8 уровней: глубокие деревья тормозят и людей, и базу.

## 3. Как это выглядит в API

**Принципы:** UUID — канонический идентификатор, путь — удобный адрес; операции CI идемпотентны; вложенность в URL не глубже двух уровней (дальше она становится неудобной, [Moesif](https://www.moesif.com/blog/technical/api-design/REST-API-Design-Best-Practices-for-Sub-and-Nested-Resources/)).

| Метод | Назначение |
|---|---|
| `GET /entities?path_prefix=fintech/&tag=env:prod` | Плоский список с фильтрами |
| `GET /entities/tree?root=<id|path>&depth=3` | Готовое дерево с агрегатами (сейчас дерево собирает фронтенд) |
| `GET /entities/by-path/{path}` | Адресация по пути |
| `PUT /entities/by-path/{path}` | **Идемпотентно создать или обновить** узел: имя, теги, владелец, репозиторий, ветка. CI описывает желаемое состояние, повторный вызов ничего не ломает |
| `POST /entities` / `PATCH /entities/{id}` | Как сейчас, для UI |
| `POST /imports` | Единая точка загрузки: `entity_id` **или** `project_path` + `auto_create` |
| `GET /findings?entity_id=X&include_descendants=true` | Находки по поддереву |
| `GET /findings/stats?entity_id=X&include_descendants=true&group_by=severity` | Агрегаты для дашборда |

Старый `POST /entities/{id}/imports` остаётся ради совместимости.

**Детали, которые экономят нервы:**
- Ответ импорта сразу отдаёт `entity_id`, `path` и `created_entities: [...]` — видно, что платформа создала сама.
- `dry_run=true` у импорта: разобрать отчёт и показать, что будет, ничего не записывая.
- Понятные коды: 409 — конфликт имён или репозиторий уже привязан к другому узлу; 422 — не та ветка.
- Токен агента (этап 6) ограничивается поддеревом: `path_prefix` в токене.

## 4. Удобство развёртывания и поддержки

Сегодняшняя история с недоступным образом MinIO показала главное: **каждый компонент — это риск**. Сейчас их пять: Postgres, Redis, MinIO, lldap, приложение.

| Решение | Эффект |
|---|---|
| **Хранилище файлов по умолчанию — диск**, S3 включается настройкой | Минимальная установка: Postgres + Redis + приложение |
| **Миграции при старте** (флаг `SV_AUTO_MIGRATE`, по умолчанию включён в docker-образе) | Не надо помнить про `alembic upgrade` |
| **Первый админ из env** | Установка в один шаг |
| **lldap — только для разработки** (профиль compose) | В проде подключается корпоративный LDAP |
| **Бэкап = `pg_dump` + папка с файлами** | Понятная инструкция на одну страницу |
| `/api/v1/health` показывает БД, Redis, хранилище и версию миграции | Быстрая диагностика |

## 5. Удобство для людей

**Разработчику** дерево не нужно: он приходит по ссылке `SV-1482` и живёт на экране «Мои уязвимости» (фильтр по его командам). Ответственность назначается автоматически (владелец узла наследуется вниз, плюс правила по путям) — как `ownedBy` в Backstage.

**AppSec** дерево нужно как карта: агрегаты по поддереву, просрочки, откуда унаследованы настройки, и очередь разбора.

**Админу** нужно, чтобы структура не требовала ручного труда: автосоздание из CI, привязка к репозиторию, теги, наследование.
