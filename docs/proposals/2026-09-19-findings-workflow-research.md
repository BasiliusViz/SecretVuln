# Как компании работают с находками: исследование процесса

**Статус:** исследование для доработки плана (не утверждено)
**Дата:** 19.09.2026
**Связано:** [2026-09-19-ai-knowledge-hub.md](2026-09-19-ai-knowledge-hub.md)

Главный вывод исследования: **находки не разбирают не из-за нехватки инструментов, а из-за процесса.** Непонятно, кто владелец, новое смешано со старым, нет сроков, исключения не имеют срока годности. ИИ ускоряет триаж, но без процесса он просто быстрее наполняет ту же свалку ([secure.com](https://www.secure.com/blog/appsec/appsec-teams-route-findings-to-code-owners), [DevX](https://www.devx.com/uncategorized/sast-triage-technical-debt/), [Хабр: Бастион](https://habr.com/ru/companies/bastion/articles/1031884/)).

## 1. Откуда и когда прилетают находки

| Момент | Что сканируется | Что с этим делают в индустрии | Отношение к SecretVuln |
|---|---|---|---|
| IDE / pre-commit | Правки разработчика | Мгновенная обратная связь | **Не к нам**: локальный инструмент |
| **PR / MR** | Изменения ветки | Показываются **только новые** находки относительно целевой ветки (baseline). Серьёзные могут блокировать merge | Проверка PR (gate), без постоянного бэклога |
| **Основная ветка** (main/master) | Весь код после merge | **Источник правды.** Бэклог строится только отсюда | Полный жизненный цикл находок |
| Ночной / плановый полный скан | Весь репозиторий, образы | Ловит новые CVE в старых зависимостях | Как основная ветка |
| Релиз / тег | Версия, которая уйдёт в прод | Отчёт для выпуска, аудит | Снимок на момент релиза |
| Рантайм | Образы в registry, DAST на стенде | Контейнеры и веб | Отдельный «объём скана» внутри актива |
| Пентест / ручной аудит | Что угодно | Ручные находки | Потом (не SARIF) |

**Как делают у GitHub:** в PR показываются только алерты из изменённого кода, вычисленные сравнением с базой целевой ветки. Бэклог по умолчанию — только основная ветка. Закрытие алерта требует **выбрать причину** из списка и по желанию добавить комментарий ([GitHub Docs: PR](https://docs.github.com/en/code-security/code-scanning/managing-code-scanning-alerts/triaging-code-scanning-alerts-in-pull-requests), [GitHub Docs: resolve](https://docs.github.com/en/code-security/how-tos/manage-security-alerts/manage-code-scanning-alerts/resolve-alerts)).

**Принцип «сначала остановить кровотечение»:** новые находки и старый бэклог — **разные очереди**. Новое разбирают сразу, пока автор помнит контекст. Старое разгребают отдельно и планово, как техдолг ([DevX](https://www.devx.com/uncategorized/sast-triage-technical-debt/), [Augment](https://www.augmentcode.com/guides/vulnerability-remediation-scan-to-merge)).

### Грабли DefectDojo, которые стоит обойти
- Модель «один пайплайн = один engagement» ломает дедупликацию: одинаковые отчёты то склеиваются, то нет (в одном случае 0 активных находок, в другом 59 на почти одинаковых данных) ([обсуждение #12983](https://github.com/DefectDojo/django-DefectDojo/discussions/12983))
- Работает только **reimport** в постоянный контейнер: сравнение с прошлым импортом, новые добавляются, **пропавшие закрываются** ([DefectDojo: Reimport](https://docs.defectdojo.com/import_data/import_intro/reimport/))
- У импорта хранятся ветка, коммит, версия и build ID — для истории и аудита

### Что это значит для SecretVuln
У нас уже правильная основа: находка привязана к **активу** (не к запуску), дедупликация по `(entity_id, fingerprint)`. Не хватает:

1. **Метаданных импорта:** `branch`, `commit_sha`, `pipeline_url`, `source` (ci/ручной/api)
2. **Понятия «объём скана» (scan scope):** какие находки импорт *обязан был* увидеть. Ключ: `(актив, сканер, ветка, метка объёма)`. Метка нужна, когда в одном активе несколько образов или модулей: Trivy по `api:latest` не должен закрывать находки по `worker:latest`
3. **Автозакрытия:** находка из того же объёма, которой нет в новом полном скане, получает статус «Исправлена» с событием «не обнаружена при повторном скане» (на основной ветке). Для частичных сканов: флаг импорта `close_missing=false`
4. **Разделения по веткам.** Варианты:
   - **A (рекомендую для v1).** Бэклог — только основная ветка (настраивается на уровне актива, по умолчанию `main`/`master`). Скан PR отправляется в отдельный эндпоинт `POST /entities/{id}/pr-checks`: сравнение с базой основной ветки, в ответе **только новые** находки и вердикт gate (прошёл / не прошёл по политике). Хранится как результат проверки, в бэклог не попадает. Решения, принятые по находке в main (например, «ложное»), действуют и в PR
   - **B.** Полное отслеживание каждой ветки (находка + «где встречается»). Мощнее, но сложнее и для v1 не нужно

## 2. Кто разбирает: роли

Типичная модель в индустрии и в российских командах ([Хабр: VK о чемпионах](https://habr.com/ru/companies/vk/articles/725088/), [Хабр: МТС](https://habr.com/ru/companies/ru_mts/articles/1063844/), [Хабр: Flowwow](https://habr.com/ru/companies/flowwow/articles/941656/), [Barrion: RACI](https://barrion.io/blog/vulnerability-remediation-lifecycle)):

| Роль | Что делает с находкой | Решения |
|---|---|---|
| **AppSec-инженер** | Триаж, настройка политик и SLA, память команды, разбор эскалаций | Подтверждает «ложное срабатывание», одобряет исключения |
| **Security Champion** (разработчик в команде) | Первичный разбор находок своей команды, эскалация сложного к AppSec | Может пометить «ложное» в своих активах (если разрешено политикой) |
| **Разработчик / команда-владелец** | Исправляет | **Запрашивает** «ложное» или исключение, но решение не за ним |
| **Тимлид / владелец продукта** | Решает, что риск можно принять (бизнес-решение) | «Риск принят» — **с обоснованием и сроком** |
| **ИИ-агент** | Предварительный разбор до человека | Только предлагает |

**Принцип двух ключей:** тот, кто исправляет, не должен единолично закрывать находку как «ложную» или «риск принят». Разработчик **запрашивает**, AppSec или владелец **одобряет** ([DevX](https://www.devx.com/uncategorized/sast-triage-technical-debt/), [secure.com: SLA](https://www.secure.com/blog/vulnerability-remediation-slas)).

**Принятие риска всегда с датой окончания.** После неё находка автоматически переоткрывается. Записываются кто одобрил и почему — этого требуют аудиторы ISO 27001 и NIS2, у нас — ФСТЭК ([secure.com: SLA](https://www.secure.com/blog/vulnerability-remediation-slas), [Strobes](https://strobes.co/blog/service-level-agreements-sla-for-vulnerability-management/)).

### Жизненный цикл (предложение)

```
           ┌──────────── ИИ-предложение (вердикт + уверенность) ─────────┐
           ▼                                                             │
импорт → Новая ──триаж──→ Подтверждена ──назначена──→ (в работе у команды) ──повторный скан──→ Исправлена
           │                                                                          (не обнаружена)
           ├── запрос «ложное» (разработчик/ИИ) ──одобрение AppSec──→ Ложное срабатывание
           └── запрос исключения ──одобрение владельца──→ Риск принят (до ДД.ММ.ГГГГ) ──истёк срок──→ Новая
```

Статусы, которые уже есть, подходят. Добавляется **запрос решения** (отдельный объект, а не статус): кто, что предлагает, причина, кто одобрил или отклонил. Новые права в Casbin: `finding:triage` (предложить), `finding:approve` (одобрить исключение или ложное).

## 3. Ответственные

**Главная проблема индустрии:** находку увидели, но непонятно, чья она. Без заранее заданной принадлежности ручная раздача становится узким местом ([secure.com](https://www.secure.com/blog/appsec/appsec-teams-route-findings-to-code-owners)).

**Источники принадлежности** (от простого к сложному):
1. **Владелец актива.** Команда, назначенная на узел дерева активов, **наследуется вниз по дереву** (можно переопределить на дочернем узле). У нас это естественно ложится на **группы пользователей**: ручные и LDAP-группы уже есть, это и есть «команды»
2. **Правила по путям** (аналог CODEOWNERS). В активе задаётся соответствие «маска пути → команда», например `app/payments/** → Команда платежей`. Задаётся в UI; позже можно импортировать файл CODEOWNERS из репозитория
3. **Конкретный человек.** По желанию: назначение вручную или по автору коммита, если CI передаёт его в метаданных импорта. По умолчанию назначаем **команду**, а не человека: люди уходят в отпуск, команды остаются
4. **Запасной вариант:** очередь AppSec, если ничего не подошло

**Монорепо:** если код общий, назначается один **основной** владелец, иначе «общая ответственность» превращается в ничью ([secure.com](https://www.secure.com/blog/appsec/appsec-teams-route-findings-to-code-owners)).

**Уведомления:** не по каждой находке (это спам), а **дайджестом** — «у вашей команды 3 новые подтверждённые, 1 просрочена». Каналы для российского рынка: Telegram, Mattermost, VK Teams, почта. Трекеры (Jira, YouTrack, GitLab Issues) — позже, с группировкой однотипных находок в одну задачу.

## 4. Сроки (SLA)

Типовые сроки по отрасли ([secure.com](https://www.secure.com/blog/vulnerability-remediation-slas), [Cogent](https://www.cogent.com/academy/vulnerability-remediation-slas-how-to-set-them), [Decryption Digest](https://www.decryptiondigest.com/blog/vulnerability-management-program-metrics-kpi-guide)):

| Критичность | Срок (типично) |
|---|---|
| Критичная | 7–15 дней (24–72 ч, если снаружи и эксплуатируется) |
| Высокая | 30 дней |
| Средняя | 60–90 дней |
| Низкая | 90–180 дней |

**Как устроить у нас:**
- Политика SLA настраивается **в UI** (не в конфиге): сроки по критичности, можно переопределить на поддереве активов (прод-сервисы строже)
- Модификаторы по данным: **в каталоге KEV** — срок сокращается (например, до 7 дней); высокий EPSS — повышение приоритета
- **Когда начинается отсчёт:** с появления находки в основной ветке. Решение «ложное» или «риск принят» останавливает отсчёт; истечение исключения запускает его заново
- У находки появляется поле `due_at`. В интерфейсе «Просрочена» / «Осталось N дней», на дашборде — доля находок в рамках SLA

## 5. Метрики программы

- **MTTR** (среднее время до исправления) по критичности и командам
- **Доля в SLA** и число просроченных
- **Тренд бэклога:** появилось против закрыто за неделю («остановили ли кровотечение»)
- **Доля ложных по правилу и сканеру.** Отчёт «шумные правила»: правило с 90% ложных срабатываний — кандидат на отключение или настройку в самом сканере. Это самый дешёвый способ уменьшить шум, до всякого ИИ
- **Согласие людей с ИИ** (после этапа ИИ)

## 6. Где в этом процессе ИИ

| Точка | Что делает ИИ | Эффект |
|---|---|---|
| Сразу после импорта | Предварительный вердикт по каждой новой находке | Чемпион открывает уже разобранную очередь |
| Проверка PR | Комментарий в MR: «вот что нового и почему это важно» | Разработчик чинит, пока помнит контекст |
| Запросы «ложное» | Проверяет обоснование, ищет похожие решения | AppSec одобряет быстрее |
| Память команды | Предлагает правило по повторяющимся решениям | Меньше повторного ручного труда |
| Шумные правила | Объясняет, почему правило шумит в этом проекте | Настройка сканеров |
| Старый бэклог | Пакетный разбор с сортировкой по уверенности | Разгребание техдолга |

По данным Flowwow (Хабр): ИИ с контекстом кода по 9 критериям снизил число ложных срабатываний на 50–60% ([Хабр](https://habr.com/ru/companies/flowwow/articles/941656/)).

## 7. Что меняется в модели данных

| Изменение | Зачем |
|---|---|
| `imports`: `branch`, `commit_sha`, `pipeline_url`, `source`, `scan_scope`, `close_missing` | Ветки, объём скана, автозакрытие |
| `entities`: `default_branch` (с наследованием), `owner_group_id` (с наследованием) | Какая ветка — бэклог; кто владелец |
| `ownership_rules`: entity_id, маска пути, group_id, приоритет | Аналог CODEOWNERS |
| `findings`: `assignee_group_id`, `assignee_user_id`, `due_at`, `cve` | Ответственный, срок, связь с CVE |
| `finding_events` | История и аудит |
| `decision_requests`: finding_id, запрошено (FP / исключение), причина, срок исключения, автор, одобривший, статус | Принцип двух ключей |
| `sla_policies`: область (поддерево), сроки по критичности, модификаторы KEV/EPSS | Сроки |
| `pr_checks`: entity_id, ветка, коммит, новые находки, вердикт | Проверка PR без засорения бэклога |
| Права: `finding:approve`, `pr_check:write` | Одобрения, загрузка из CI |

`uploaded_by_id` у импорта уже есть.
