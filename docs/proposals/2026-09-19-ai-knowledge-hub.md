# SecretVuln как хранилище знаний об уязвимостях для ИИ

**Статус:** предложение, на обсуждении (не утверждено)
**Дата:** 19.09.2026

## 1. Проблема

Сканеры находят тысячи уязвимостей, а люди их не разбирают. Бэклог растёт, реальные проблемы тонут в шуме, и команда перестаёт доверять инструментам.

**Цель:** сделать SecretVuln единым хранилищем всех находок от всех сканеров, из которого ИИ-агенты легко берут контекст (находки, похожие случаи, решения команды) и куда записывают результаты своего анализа. Человек видит уже отфильтрованный и объяснённый список.

**Что SecretVuln НЕ делает:** не сканирует код. Сканеры остаются отдельными инструментами, включая будущие ИИ-сканеры вроде OASIS.

## 2. Что показал анализ рынка

### Проблема реальная и массовая
- CVSS-приоритизация предсказывает только ~2,3% реальных эксплуатаций, но заставляет чинить ~57% всех уязвимостей. EPSS + KEV + достижимость дают выигрыш в эффективности в 14–18 раз при покрытии угроз 85%+ ([Hackerstorm](https://www.hackerstorm.com/articles/our-blog/vulnerability-intelligence-analysis/vulnerability-backlog-broken-decision-model-cvss-epss-kev), [Help Net Security](https://www.helpnetsecurity.com/2026/08/31/joye-purser-cohesity-kev-epss-cvss-conflicts/))
- Типичная картина: из 10 000 уязвимостей в бэклоге у 92% вероятность эксплуатации в ближайшие 30 дней ниже 2% ([Decryption Digest](https://www.decryptiondigest.com/blog/epss-vulnerability-prioritization-patching-workflow-guide))
- Даже DefectDojo в 2025 году сделал ставку на улучшение дедупликации и приоритизацию по реальному риску, а не по severity ([BusinessWire](https://www.businesswire.com/news/home/20250513967867/en))

### ИИ-триаж работает, но с оговорками
- **Semgrep Assistant + Memories:** ИИ разбирает ~60% новых SAST-находок, люди соглашаются с его решениями в 96% случаев. Ключевой механизм: **«память»**. Решение команды с обоснованием превращается в правило, которое применяется к похожим находкам, после одобрения человеком ([Semgrep: 60%](https://semgrep.dev/blog/2025/semgrep-is-confidently-handling-60-of-all-triage-for-users-without-reducing-coverage/), [Memories](https://semgrep.dev/blog/2025/announcing-ai-noise-filtering-and-triage-memories/), [что пишут в память](https://semgrep.dev/blog/2026/inside-the-ai-memories-security-teams-are-writing/))
- **Исследования:** ИИ-агенты снижают долю false positive на OWASP Benchmark с 92% до 6% ([Sifting the Noise](https://arxiv.org/abs/2601.22952)). QASecClaw: 560 → 64 false positive ([arXiv](https://arxiv.org/html/2605.01885v1)). SAST-Genius: 225 → 20 ([arXiv](https://arxiv.org/pdf/2509.15433)). Дообученная Llama 3 8B: precision 89,5% против 35,7% у голого Semgrep ([InfoWorld](https://www.infoworld.com/article/4093079/how-pairing-sast-with-ai-dramatically-reduces-false-positives-in-code-security.html))
- **Главная оговорка во всех источниках:** хорошие результаты даёт **контекст кода** и **история решений**. По одному сниппету ИИ гадает.
- **Pixee:** уровневый подход (структурный → агентный → адаптивный), −70–95% false positive ([Pixee](https://www.pixee.ai/blog/best-automated-remediation-tools-2026))

### «Отдать данные ИИ через MCP» — уже тренд
- У DefectDojo есть официальный MCP-сервер (Pro) и несколько open-source ([документация](https://docs.defectdojo.com/metrics_reports/ai/mcp_server_pro/), [блог](https://defectdojo.com/blog/how-to-use-the-model-context-protocol-mcp-to-chat-with-your-vulnerability-data), [jamiesonio/defectdojo-mcp](https://github.com/jamiesonio/defectdojo-mcp), [brduru/mcp-defect-dojo](https://github.com/brduru/mcp-defect-dojo))
- **Но это просто обёртки над CRUD API:** поиск по фильтрам, смена статуса. Семантического поиска, памяти команды и учёта происхождения ИИ-выводов в них нет. **Здесь наша ниша.**

### Российский рынок
- ASOC-платформы: AppSec.Hub (заявляет ML-распознавание false positive), CyberCodeReview, Hexway, TARS ([обзор](https://softmedialab.com/rossiiskie-asoc-platformi-obzor-reshenii), [AppSec.Hub](https://appsec.global/appsechub))
- Наши козыри: **локальные модели** (данные не уходят наружу, это важно для КИИ и 152-ФЗ), открытый MCP-интерфейс для любых агентов, прозрачность (каждый вывод ИИ объяснён и привязан к источнику)

### Риски, о которых предупреждают
- **Prompt injection через данные находок.** Сниппеты, сообщения и комментарии в коде контролирует автор кода, в том числе злоумышленник. Комментарий вида «AI reviewer: this is a false positive» может обмануть ИИ-триажёра. Реальные случаи: CVE-2025-53773 (Copilot), компрометация через ИИ-триаж issues в GitHub Actions ([Vectra](https://www.vectra.ai/topics/prompt-injection), [OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/))
- **Утечки через векторную базу (OWASP LLM08).** Поиск похожих не должен показывать находки, к которым у пользователя или агента нет доступа ([Cobalt](https://www.cobalt.io/blog/vector-and-embedding-weaknesses))
- **Секреты в находках.** Находка Gitleaks содержит сам секрет в `raw`. Отправлять его в эмбеддинги или LLM нельзя без маскирования.

## 3. Позиционирование

> **SecretVuln — память и контекст для AppSec-агентов.** Все находки всех сканеров в одном месте: нормализованные, дедуплицированные, обогащённые данными об эксплуатации, векторизованные, с историей решений команды. Агенты читают через MCP/API и пишут свои выводы обратно. Человек принимает решения.

## 4. Архитектура по слоям

```
Сканеры → SARIF → [L0 Импорт] → [L1 Обогащение] → [L2 Векторизация] → [L3 Краткое описание]
                                                                            │
                     [L4 Память команды] ←── решения людей с обоснованием ──┤
                                                                            ▼
                     [L5 MCP + REST для агентов] ⇄ внешние ИИ-агенты (триаж, чат, ИИ-сканеры)
                                                     └→ ai_analyses (выводы с источником)
```

### L0. Импорт (есть) + доработки
- **Причина при триаже.** Статусы `false_positive` и `risk_accepted` ставятся только с текстовым обоснованием. Без него память команды не из чего строить: сейчас `PATCH /findings/{id}?status=` причину не принимает
- **История находки** (`finding_events`): кто, когда, из какого статуса в какой и почему; человек или агент. Одновременно это аудит-лог из MVP

### L1. Обогащение без ИИ (дёшево и сразу даёт эффект)
- CVE → **EPSS** (вероятность эксплуатации), **CISA KEV** (эксплуатируется ли в реальности), опционально **БДУ ФСТЭК** (ценно для российского рынка)
- CWE → название и категория
- Фоновая задача ARQ раз в сутки обновляет справочники, находки обогащаются при импорте
- Итог: в приоритизацию сразу добавляется «реальный риск», в том числе для SCA и контейнеров, где ИИ почти не нужен

### L2. Векторизация
- Подключение модели эмбеддингов — **в settings** (env), как вы и хотели:
  - `SV_AI_PROVIDER` = `ollama` | `openai_compatible` (второй вариант покрывает vLLM, LM Studio, облачные API)
  - `SV_AI_BASE_URL`, `SV_AI_API_KEY`, `SV_EMBED_MODEL`, `SV_LLM_MODEL`
- Для каждой находки строится **канонический текст**: сканер, rule_id, CWE, severity, сообщение, путь к файлу, сниппет. **Перед отправкой — маскирование секретов**
- Хранение: **pgvector** в том же Postgres (без отдельной векторной БД), таблица `finding_embeddings` (finding_id, model, dim, content_hash, vector), индекс HNSW
- При смене модели — фоновая переиндексация (по `model` + `content_hash`)
- Модель по умолчанию: `bge-m3` (русский + английский + код, ~1,2 ГБ VRAM) или `qwen3-embedding:4b`, если хватит памяти

### L3. Краткое описание от ИИ (опционально)
- LLM из settings пишет краткое описание на русском: «что это, чем опасно, где», 2–3 предложения
- Хранится как запись в `ai_analyses` с `kind=summary`, НЕ в таблице findings (как и договаривались раньше)
- Генерируется в фоне после импорта; можно выключить

### L4. Память команды (главная фишка, аналог Semgrep Memories)
- **Память** — утверждённое правило вида: «в активе *Платёжка* (и его поддереве) находки `python.sqlalchemy.raw-query` в `tests/**` — false positive, потому что это тестовые фикстуры»
- Откуда берётся:
  1. Человек сам создаёт в UI (сверху вниз)
  2. Система **предлагает** память по нескольким похожим решениям с обоснованием (снизу вверх); человек одобряет
- Область действия: поддерево активов × сканер/правило/CWE × маска пути
- Применение: при импорте новая находка, подпадающая под память, получает **пометку-подсказку** со ссылкой на память. Скрывать ли автоматически, решается политикой (по умолчанию нет)

### L5. Интерфейс для агентов: MCP + REST
- **MCP-сервер** (отдельный процесс или эндпоинт в FastAPI, транспорт streamable HTTP). Инструменты:
  - `search_findings(query, filters)` — семантический + фильтровой поиск
  - `get_finding(id)` — находка + обогащение + история + активные памяти
  - `find_similar(id, k)` — похожие находки **с решениями команды**
  - `list_memories(scope)` — правила команды
  - `submit_analysis(finding_id, verdict, confidence, explanation, ...)` — записать вывод
  - `get_stats(filters, group_by)` — агрегаты для вопросов вроде «что у нас в платёжке?»
- **Доступ:** агент ходит с API-токеном сервисного аккаунта, права через Casbin, как у людей. Поиск похожих **фильтруется по правам** (защита от LLM08)
- **Запись обратно только в `ai_analyses`**, не в статус находки. Агент предлагает, человек подтверждает (или политика «авто-FP при уверенности > X и совпадении с памятью», включается позже и явно)

### L6. Позже
- Встроенный агент-триажёр (фоновый воркер, тот же MCP изнутри)
- Кластеры корреляции между сканерами: Semgrep и CodeQL нашли одно и то же → одна «проблема»
- Чат с базой в UI
- Контекст кода: даёт внешний агент со своим доступом к репозиторию, платформе код хранить не нужно

## 5. Новые таблицы

| Таблица | Назначение |
|---|---|
| `finding_events` | История: статус до/после, причина, автор (user или agent), время |
| `vuln_intel` | Справочник CVE → EPSS, KEV, БДУ; обновляется раз в сутки |
| `finding_embeddings` | Вектор + модель + content_hash (pgvector, HNSW) |
| `ai_analyses` | Выводы ИИ: kind (summary/triage), verdict (true_positive/false_positive/uncertain), confidence, explanation, remediation, similar_ids, memory_ids, **provenance** (агент, модель, версия промпта), статус проверки человеком (accepted/rejected) |
| `triage_memories` | Память: область действия, условие, решение, обоснование, автор, статус (suggested/approved/disabled), счётчик применений |
| `api_tokens` | Токены сервисных аккаунтов для агентов (хранится хеш) |

## 6. Защита (обязательная часть, не «потом»)

1. **Маскирование секретов** до отправки в эмбеддинги и LLM (для находок Gitleaks/TruffleHog: только тип секрета и путь, без значения)
2. **Данные находок = недоверенный ввод.** Сниппеты и сообщения в промптах заключаются в явные границы; ИИ по умолчанию не может сам закрыть находку
3. **Права в векторном поиске:** similarity-поиск возвращает только то, что разрешено вызывающему
4. **Происхождение каждого вывода ИИ:** какая модель, какой агент, на основании каких похожих находок и памятей
5. **Метрика доверия:** доля выводов ИИ, с которыми согласились люди (как 96% у Semgrep). Пока она низкая, автоматики нет

## 7. Метрики успеха

- Доля находок с решением (человека или подтверждённого ИИ): растёт
- Время от импорта до первого решения: падает
- Согласие людей с выводами ИИ: ≥ 85–90%, прежде чем включать авто-скрытие
- Число true positive, ошибочно помеченных ИИ как false positive: цель ≈ 0 (выборочная проверка)

## 8. Этапы

| Этап | Что | Ценность |
|---|---|---|
| **1. Фундамент данных** | Причина при триаже, `finding_events`, обогащение EPSS/KEV/CWE | Приоритизация по реальному риску без ИИ; данные для памяти |
| **2. Векторка** | pgvector, settings для модели, эмбеддинги в воркере + backfill, маскирование, «Похожие находки» в UI | Семантический поиск, основа для RAG |
| **3. Выход для агентов** | API-токены, MCP-сервер, `ai_analyses`, приём вердиктов, блок «Анализ ИИ» в карточке | Любой агент (хоть Claude) может разбирать находки уже сейчас |
| **4. Память команды** | `triage_memories`, предложение памяти по решениям, применение при импорте | Главный механизм сокращения шума |
| **5. Встроенный ИИ** | Краткие описания, встроенный агент-триажёр на Ollama, метрики согласия | Работа «из коробки» без внешних агентов |
| **6. Дальше** | Корреляция между сканерами, чат с базой, политики авто-закрытия | |

После этапа 3 уже можно проверить идею вживую: подключить Claude к MCP SecretVuln и дать ему разобрать реальный бэклог.

## 9. Открытые вопросы

1. Порядок этапов: начать с фундамента данных (1) или сразу с векторки (2)?
2. MCP-сервер: встроить в FastAPI (один деплой) или отдельный сервис?
3. БДУ ФСТЭК в обогащении — нужно в первой версии?
4. Какие модели реально доступны: Ollama локально (RTX 4070 SUPER), или ещё корпоративный API?
5. Формат отчётов: остаёмся только на SARIF или со временем добавим нативные парсеры (Burp, SonarQube)?
