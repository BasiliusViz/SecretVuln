# Этап 4 «Права на поддерево проектов» — дизайн

Дата: 2026-10-05. Статус: согласован в брейншторме, ждёт просмотра.

## Цель

Права перестают быть глобальными: команде даётся роль на ветку дерева проектов. Тимлид сам раздаёт доступ к своей ветке, не превышая собственных прав. Заодно закрывается вопрос этапа 3: смена SLA-политики проекта требует отдельного права `sla:assign`.

## Решения

| Вопрос | Решение |
|---|---|
| Как задаётся область | Явная привязка: группа + роль + проект (`NULL` — всё дерево) |
| Хранение | Своя таблица `role_bindings`; Casbin остаётся только для матрицы «роль → права» |
| Видимость выше своей ветки | Предки видны заглушкой (имя/путь), соседние ветки не видны |
| SLA проекта | Новое право `sla:assign` на поддерево |
| Назначение находки на группу без доступа | Разрешено, доступа не даёт; UI предупреждает |
| Делегирование | Да: право `access:manage`, правило «не сильнее своих» |

Отвергнуто: настоящие Casbin-домены (не строят SQL-фильтр для списков, домен-строка ломается при переименовании узла) и доступ через `owner_group_id` (сливает владение и доступ).

## Модель данных

`role_bindings`: `id`, `group_id` → `user_groups` (CASCADE), `role_id` → `roles` (CASCADE), `entity_id` → `entities` (NULL = всё дерево, CASCADE), `created_at`, `created_by` → `users` (SET NULL). Уникальность `(group_id, role_id, entity_id)` с `NULLS NOT DISTINCT`.

Привязка ссылается на `entity_id`, а не на путь: переименование и перенос узла доступ не ломают.

Миграция: каждая строка `group_roles` → привязка с `entity_id = NULL`; `group_roles` удаляется. Существующие пользователи сохраняют доступ.

## Каталог прав

- **Действуют на поддерево**: `entity:read/write/delete`, `finding:*`, `import:*`, `sla:assign` (новое), `access:manage` (новое).
- **Только глобальные**: `group:write/delete`, `role:*`, `sla:manage`. В привязке к проекту игнорируются; UI ролей помечает их «только глобально», диалог привязки предупреждает.
- **Исключение**: `group:read` и `sla:read` действуют из любой привязки — без них команда не может назначить находку и увидеть свою политику. Компромисс: список групп с участниками (имена, email) виден всем, у кого есть хоть одна привязка.

Встроенная роль в `seed-roles`: «Руководитель команды» — `entity:read/write`, `finding:read/triage`, `import:read/import`, `sla:read`, `sla:assign`, `access:manage`, `group:read`.

## Вычисление доступа

На каждый запрос `load_access(db, user)` одним запросом собирает: группы пользователя → привязки → `path_cache` узла (или «всё дерево») → права роли из `casbin_rule` (читаем из БД, а не из in-memory enforcer: иначе правка роли не видна другим процессам API).

Результат — `Access`: для каждого права либо «везде», либо набор префиксов путей. Вложенные префиксы схлопываются (`fintech` поглощает `fintech/payments`).

- Узел E разрешён, если `path_cache(E) == p` или начинается с `p + "/"` (PG `starts_with`, без LIKE-масок).
- Права только складываются, запретов нет.
- `is_superuser` → «везде» по всем правам. Подмешивание роли-строки `"superuser"` убирается.
- JWT больше не несёт роли; токен только удостоверяет пользователя. Изменения привязок и ролей действуют со следующего запроса.

## Видимость

- Любое право на X открывает **заглушку** X и всех его предков: `id`, `name`, `slug`, `parent_id`, `path_cache`, `stub: true`. Полная карточка, настройки, находки, счётчики — только по соответствующему праву.
- Заглушки предков в деталях не открываются: `GET /entities/{ancestor}` → 404.
- Осознанная утечка: в настройках своего проекта видны унаследованные значения и имя предка-источника («унаследовано от fintech»).
- Нет права на чтение объекта → **404** (номера `SV-N` сквозные, 403 выдавал бы существование). Чтение есть, действия нет → **403**.

## Структура дерева

- Корневой проект — только глобальный `entity:write`; дочерний — `entity:write` на родителе.
- Перенос: `entity:write` на узле и на новом родителе (в корень — глобально). Если меняется эффективная SLA-политика узла — ещё `sla:assign` на узле.
- Удаление: `entity:delete` на узле; привязки узла удаляются каскадом.
- Импорт с автосозданием узлов по пути: `entity:write` на ближайшем существующем предке; новый корень — глобально.

## Делегирование

- `access:manage` на N позволяет добавлять и удалять привязки на N и потомках.
- **«Не сильнее своих»**: выдать роль R на N можно, только если каждое действующее на поддереве право R есть у выдающего на N. Глобальные права роли не учитываются (в привязке к проекту они не действуют).
- **Отзыв** — по тому же правилу: нельзя снять привязку, роль которой сильнее ваших прав на узле (тимлид не снимет AppSec).
- Глобальные привязки создаёт и удаляет только глобальный `group:write`.
- Группа выбирается из существующих; состав групп правит только глобальный `group:write`.
- Роль с `access:manage` выдать можно (второй тимлид на ветке). Урезание прав тимлида не отзывает выданные им привязки.

## API

**Общие блоки** — `services/access.py`: `Access.allows(perm, entity)`, `Access.filter(perm, path_column)`, `Access.anywhere(perm)`. `api/deps.py`: зависимость `get_access`; `require_permission` = «право есть хоть где-то» (ворота эндпоинта); `ensure(access, perm, entity)` → 404/403.

**Точечные** (загрузили объект → `ensure` по его проекту):

| Эндпоинты | Проверка |
|---|---|
| Проект: get, patch, delete, settings, ownership-rules, unpin, config.yml, reassign, by-path | право на узел; перенос и SLA — см. «Структура дерева»; смена `sla_policy_id` — `sla:assign` |
| Находка: get, by-number, events, patch, assign, help, decisions | право на проект находки |
| Решения approve/reject | `finding:approve` на проекте находки |
| Импорт: загрузка (оба варианта) | `import:import` на целевом узле |
| `GET /imports/{id}`, `GET /entities/{id}/imports` | `import:read` на проекте |
| `POST /findings/bulk` | всё или ничего: 404, если хоть одна не читается; 403, если на какую-то нет права |

**Списки** (SQL-фильтр по праву):

| Эндпоинт | Право |
|---|---|
| `GET /entities` | `entity:read` (полные) + заглушки по любому праву |
| `GET /tags` | `entity:read` |
| `GET /findings`, `/findings/stats`, `/findings/noisy-rules`, `POST /metrics/aggregate` | `finding:read` |
| `GET /decisions` | `finding:read`; кнопки одобрения — по `finding:approve` на проекте |
| `GET /imports` | `import:read` |

Параметр `entity_id` с недоступным проектом в любом списке → 404.

**Привязки**:
- `GET /entities/{id}/bindings` — свои и унаследованные (с источником); право `entity:read` на узле. Если у вызывающего есть `access:manage` на узле, ответ включает `roles`: каждая роль с `grantable` и списком `missing` (каких прав не хватает).
- `POST /entities/{id}/bindings`, `DELETE /bindings/{id}` — `access:manage` + «не сильнее своих».
- `GET/POST/DELETE /groups/{id}/bindings` — все привязки группы; глобальные — только глобальный `group:write`. Заменяют эндпоинты добавления и удаления ролей группы.
- `GET /groups?entity_id=X` — флаг `has_access` (`finding:read` на X) для предупреждения при назначении.

**`/auth/me`**: `permissions` — «есть хоть где-то» (меню); `scoped_permissions: {"finding:read": "*" | ["fintech/payments", …]}` — для кнопок. `/permissions/catalog` помечает глобальные права.

Воркер (`process_import`, `expire_risks`) не меняется: проверка делается при загрузке.

## Фронтенд

- `AuthContext.can(perm, path?)`: без пути — «хоть где-то», с путём — проверка префикса.
- «Проекты»: заглушки предков серые, некликабельные.
- `FindingWindow`, `ProjectSettings`, `Findings`, `Inbox`: кнопки через `can(perm, entity.path)`.
- Проект → вкладка «Доступ»: свои привязки (добавить/удалить) и унаследованные (только просмотр, «от fintech»); недоступные роли — с подсказкой, каких прав не хватает.
- «Группы»: вместо ролей группы — список привязок «роль → область».
- «Роли»: значок «только глобально».
- Диалог назначения: предупреждение «у группы нет доступа к проекту».
- Все строки — в `i18n/ru.json`.

## Тесты

- Юнит `Access`: префиксы и граница `/`, схлопывание, объединение, игнор глобальных прав в привязке к проекту, исключение `group:read`/`sla:read`, суперюзер.
- Матрица «две команды × две ветки»: каждый список отдаёт только своё; точечные — 404/403 где должны; `by-number` чужой находки → 404.
- Делегирование: роль сильнее своей → 403; снять привязку AppSec → 403; глобальные привязки → 403; второй тимлид — ок.
- Перенос: права на обе ветки; `sla:assign` при смене эффективной политики; перенос в корень — только глобально.
- Импорт с автосозданием узлов.
- Правка роли действует без перелогина.
- Миграция: `group_roles` → глобальные привязки.
- `conftest`/`factories` переводятся на привязки.

## Порядок работы

Две сессии: бэкенд (миграция, `Access`, эндпоинты, тесты) → записка в `docs/` → фронтенд. Одно ревью `sv-reviewer` в конце этапа.

## Не делаем

Запреты (deny); делегирование состава групп; права на отдельную находку; аудит-лог (следующий этап); ограничение `role:write` (по-прежнему равен админу).
