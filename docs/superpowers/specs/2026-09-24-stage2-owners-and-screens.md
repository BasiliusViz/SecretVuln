## 1. Задача 0: хранилище файлов

- Настройка `SV_STORAGE_BACKEND` = `local` (по умолчанию) | `s3`; `SV_STORAGE_PATH` (по умолчанию `./data/sarif`).
- `app/services/storage.py`: `save_sarif(bytes, filename) -> key`, `load_sarif(key) -> bytes`; две реализации (диск, S3). `s3.py` становится реализацией S3.
- Колонка `imports.s3_key` → `storage_key` (миграция-переименование). Ключи вида `imports/<uuid>/<имя>` одинаковы для обоих бэкендов.
- Защита от выхода из папки: имя файла очищается, итоговый путь проверяется на нахождение внутри `SV_STORAGE_PATH`.
- `docker-compose.yml`: MinIO уходит в профиль `s3`, образ закрепляется на рабочем теге. `/api/v1/health` показывает бэкенд хранилища и его доступность.
- Старые импорты в MinIO: при `local` их файлы недоступны для ре-нормализации — находки остаются в БД, это приемлемо для dev.

## 2. Путь как адрес и автосоздание из CI

### 2.1. Модель
- `entities.slug` — адресная часть узла: `[a-z0-9._-]`, 1–100 символов. Уникален среди соседей (`uq_entities_parent_slug`, NULLS NOT DISTINCT). Для существующих узлов генерируется миграцией из имени (транслитерация кириллицы, при конфликте — суффикс `-2`). В UI редактируется отдельно от имени.
- `entities.path_cache` — полный путь `fintech/payments/backend-api`, уникальный индекс + индекс для поиска по префиксу. Пересчитывается для всего поддерева при смене slug или родителя (одним UPDATE по префиксу).
- UUID остаётся основным идентификатором; ссылки в UI — по UUID.

### 2.2. API
| Метод | Назначение |
|---|---|
| `GET /entities/by-path/{path}` | Узел по пути |
| `PUT /entities/by-path/{path}` | Идемпотентно создать узел (и недостающих предков) или обновить поля. Право `entity:write` |
| `POST /imports` | Единая точка загрузки: `entity_id` **или** `project_path` (+ `auto_create=true`). Остальные поля — как у `POST /entities/{id}/imports`, плюс `config` (файл `.secretvuln.yml`) |
| `GET /findings?entity_id=X&include_descendants=true` | Находки поддерева (через `path_cache`); то же для `/findings/stats` |

- Автосоздание требует у пользователя/токена **и** `import:import`, **и** `entity:write`; без второго — 403 с понятным текстом.
- Ответ импорта дополняется `entity_path` и `created_entities: [{id, path}]`.
- Имя автосозданного узла = его slug.
- Старый `POST /entities/{id}/imports` остаётся.

### 2.3. Репозиторий как ключ
`repo_url` (раздел 4) нормализуется (без `.git`, без завершающего `/`, в нижнем регистре хост) и уникален среди узлов. Попытка привязать тот же репозиторий ко второму узлу → 409 «Репозиторий уже привязан к проекту <путь>».

## 3. Настройки проекта: файл + админка

### 3.1. Поля
Наследуемые вниз по дереву (NULL = «унаследовано»): `default_branch` (уже есть), `owner_group_id`, `repo_url`, `repo_type` (`gitlab|github|gitea|bitbucket`), `repo_path_prefix`. Плюс список правил владения (раздел 4.2).

### 3.2. Файл `.secretvuln.yml`
```yaml
version: 1
default_branch: main
owner: payments-team            # имя группы пользователей
repo:
  url: https://gitlab.corp/fintech/payments
  type: gitlab
  path_prefix: services/api      # для монорепо
ownership:
  - path: "app/payments/**"
    owner: payments-team
  - path: "app/auth/**"
    owner: identity-team
```
- CI прикладывает файл к импорту (`-F config=@.secretvuln.yml`). Применяется синхронно в API до постановки задачи в очередь — владельцы нужны воркеру.
- Неверный формат/схема → 422, импорт не создаётся (CI падает сразу и понятно).
- Неизвестная группа или недопустимое значение → поле пропускается, предупреждение в ответе импорта и в `imports.config_warnings`.
- Узел хранит последнее применённое содержимое: `entities.config_file` (JSONB), `config_commit_sha`, `config_applied_at`.

### 3.3. Закрепление полей
- `entities.pinned_fields` — список полей, изменённых вручную в админке (`owner_group_id`, `default_branch`, `repo`, `ownership_rules`).
- При применении файла закреплённые поля пропускаются; остальные перезаписываются значениями из файла.
- Правка поля в админке закрепляет его. «Вернуть к файлу» снимает закрепление и сразу подставляет значение из сохранённого `config_file`.
- Правила владения закрепляются **целиком списком**: правка любого правила в админке закрепляет весь список.
- В админке у каждого поля — источник: «из файла», «вручную», «унаследовано от <путь>».
- Кнопка «Скачать .secretvuln.yml» — выгружает текущие действующие настройки узла, чтобы команда обновила файл в репозитории.
- Настройки узла можно задать и без файла — только в админке (всё тогда «вручную»).

## 4. Владельцы

### 4.1. Модель
- `entities.owner_group_id` → `user_groups.id` (ON DELETE SET NULL), наследуется.
- `ownership_rules`: entity_id, `pattern` (glob: `**`, `*`, `?`), group_id, `position` (порядок), `source` (`file|manual`).
- У находки: `assignee_group_id`, `assignee_user_id` (необязателен, ручной), `assigned_manually` (bool).

### 4.2. Назначение
Порядок поиска команды для находки:
1. Правила узла находки, затем правила предков вверх по дереву; внутри узла — по `position`, первое совпадение `file_path` с маской.
2. Владелец узла (с наследованием).
3. Никто → «без владельца», видна во вкладке очереди AppSec.

- Выполняется воркером при импорте: для новых находок и для всех открытых находок узла, у которых `assigned_manually = false` (так изменения правил доезжают со следующим сканом).
- Ручное переназначение (`POST /findings/{id}/assign {group_id, user_id}`, право `finding:triage`) ставит `assigned_manually = true`, пишет событие `assigned`.
- Кнопка «Переназначить по правилам» на узле — применить правила к открытым находкам поддерева сейчас, не дожидаясь скана.

## 6. Экраны

### 6.1. Окно уязвимости `/f/SV-N`
По общей спеке, раздел 10.1, без срока (появится в этапе 3). Детали этапа 2:
- Карточка: `GET /findings/by-number/{n}` расширяется полями `entity_path`, `assignee_group`, `assignee_user`, `code_url`, `code_url_head`, `help` (рекомендация из SARIF `help`/`rule.help`).
- Действия разработчика: «Беру в работу» (статус `in_progress`), «Ложное срабатывание» (окно с причинами → запрос), **«Нужна помощь AppSec»**.
- Действия AppSec (право `finding:approve`/`triage`): «Подтвердить», «Ложное» и «Принять риск» сразу, переназначить, одобрить/отклонить активный запрос.
- **Комментарии**: `POST /findings/{id}/comments` → событие `comment`, лента истории показывает их вместе с остальными событиями.
- **Помощь AppSec**: `POST /findings/{id}/help {text}` ставит `findings.help_requested_at` и пишет событие `help_requested`; ответ AppSec — комментарий с флагом «вопрос решён» (снимает флаг).
- Свёрнутый блок «Подробнее»: CWE, сканер, правило, импорт, история.
- «Скопировать ссылку». Строка таблицы «Уязвимости» ведёт сюда.

### 6.2. Очередь AppSec `/inbox`
Вкладки этапа 2: **Новые** · **Запросы на одобрение** · **Вопросы от команд** · **Без владельца**.
- Список: чекбокс, критичность, SV-номер, заголовок, сканер · проект · команда.
- Массовые действия: `POST /findings/bulk {ids, action: confirm|false_positive|assign, reason_tag, reason, group_id}`; `false_positive` требует `finding:approve`. Ответ — сколько применено и какие id пропущены с причиной.
- Горячие клавиши: `J`/`K` — навигация, `X` — отметить, `C` — подтвердить, `F` — ложное, `A` — назначить, `Enter` — открыть.

### 6.3. «Мои уязвимости» `/my`
Уязвимости, где `assignee_user = я` или `assignee_group` ∈ мои группы. По умолчанию статусы «Подтверждена» + «В работе», сортировка по критичности, затем по дате обнаружения (по сроку — в этапе 3). Вкладка «Мои запросы» — статусы моих запросов на «ложное»/«риск».

### 6.4. Настройки проекта
Вкладка у проекта в разделе «Проекты»: slug и путь, основная ветка, репозиторий, команда-владелец, правила владения (добавить/удалить/переставить), источник каждого поля, «Вернуть к файлу», «Скачать .secretvuln.yml», «Переназначить по правилам».

### 6.5. Таблица «Уязвимости»
Добавляются колонка «Команда», фильтр по команде и «Без владельца», флажок «Включая вложенные проекты» при фильтре по проекту.

## 7. Проверка
- pytest: хранилище (диск, защита от `../`), slug/path (пересчёт при переносе, конфликты), `PUT by-path` идемпотентен, автосоздание и 403 без `entity:write`, применение файла (закреплённые поля не трогаются, 422 на битый файл, предупреждения), назначение по правилам (порядок, наследование, `assigned_manually`), ссылки на код для 4 типов репозиториев, комментарии/помощь/массовые действия и их права.
- smoke-тест: импорт по `project_path` с `auto_create` и `.secretvuln.yml`, проверка владельца у находок.
- Браузер: bob (разработчик) — `/my`, окно уязвимости, «Нужна помощь»; alice (AppSec) — `/inbox`, массовые действия, настройки проекта.
