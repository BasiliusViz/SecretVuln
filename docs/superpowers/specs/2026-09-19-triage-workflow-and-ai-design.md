# SecretVuln: процесс разбора находок и ИИ-слой — спецификация

**Статус:** на согласовании у пользователя
**Дата:** 19.09.2026
**Основано на:** [ИИ-хранилище](../../proposals/2026-09-19-ai-knowledge-hub.md), [исследование процесса](../../proposals/2026-09-19-findings-workflow-research.md)

## 1. Цель

Находки не должны копиться. Для этого:
1. **Процесс:** у каждой находки есть владелец, срок и понятный следующий шаг. Новое не смешивается со старым. Исправление подтверждает сканер, а не человек.
2. **Удобство:** разработчику — простое окно по ссылке. AppSec — входящая очередь, которую можно разобрать до нуля.
3. **ИИ поверх процесса:** SecretVuln становится хранилищем знаний об уязвимостях (векторная база + решения команды), из которого ИИ-агенты берут контекст и куда пишут свои выводы. Решает всегда человек.

**Не входит:** сканирование (сканеры — отдельные инструменты), синхронизация с Jira (позже), проверки PR/MR (позже).

## 2. Роли и права

| Роль | Что может |
|---|---|
| **Разработчик** (член команды-владельца) | Видит находки своей команды, берёт в работу, **запрашивает** «ложное срабатывание» или «риск принят», задаёт вопрос AppSec |
| **AppSec-инженер** | Всё выше + подтверждает или отклоняет находки, **одобряет** запросы, сам ставит «ложное» сразу, настраивает владельцев, SLA и память |
| **ИИ-агент** (сервисный аккаунт) | Читает данные, пишет выводы в `ai_analyses`. Статус находки не меняет |

Новые действия Casbin (ресурс `finding`): `approve` — одобрять запросы и ставить «ложное» / «риск принят» напрямую. Уже есть: `read`, `write`, `triage`. Встроенные роли расширяются: «Инженер ИБ» получает `approve`, для разработчиков появляется встроенная роль «Разработчик» (`finding:read`, `finding:triage`).

**Правило двух ключей (решение пользователя):** разработчик пишет «ложное срабатывание», AppSec подтверждает. Пользователь с правом `approve` ставит решение сразу.

## 3. Жизненный цикл находки

**Статусы:** существующие `new`, `triaged`, `confirmed`, `false_positive`, `risk_accepted`, `fixed` + новый **`in_progress`** («В работе»).

```
импорт → Новая ──AppSec──→ Подтверждена ──разработчик «Беру в работу»──→ В работе
                                 │                                        │
                                 └──── повторный скан: не обнаружена ─────┴──→ Исправлена
Новая / Подтверждена / В работе:
   ├─ разработчик «Ложное срабатывание» → запрос → AppSec одобрил → Ложное срабатывание
   │                                            └→ AppSec отклонил → статус не меняется, причина видна разработчику
   └─ «Риск принят» (с датой окончания) → запрос → одобрено → Риск принят ──срок истёк──→ Новая
Исправлена ── снова обнаружена ──→ Новая (уже реализовано)
```

**Кнопки «Исправил» нет (решение пользователя).** «Исправлена» ставит только повторный скан (раздел 4.3).

Пока запрос на рассмотрении, находка помечена «На проверке у AppSec», статус не меняется.

**Статус `triaged` («В разборе»)** остаётся для обратной совместимости. В новых экранах основной путь — Новая → Подтверждена.

## 4. Импорт, ветки, автозакрытие

### 4.1. Метаданные импорта
`POST /entities/{id}/imports` принимает дополнительные поля формы (все необязательные):
`branch`, `commit_sha`, `pipeline_url`, `scan_scope` (метка объёма, например имя образа), `close_missing` (по умолчанию `true`).
`source` вычисляется: `manual` (UI) или `api` (токен).
Если ветка или коммит не переданы, воркер берёт их из SARIF `runs[].versionControlProvenance` (`branch`, `revisionId`, `repositoryUri`).

### 4.2. Бэклог — только основная ветка
- У актива есть `default_branch`, наследуется вниз по дереву; значение по умолчанию — не задано (любая ветка считается основной, как сейчас).
- Импорт с веткой, отличной от основной, отклоняется с понятной ошибкой: «Ветка feature/x не основная для актива. Проверки веток появятся позже». Ручная загрузка без ветки считается основной.

### 4.3. Автозакрытие
- **Объём скана** = `(entity_id, scanner, scan_scope)`. После успешного импорта с `close_missing=true` все открытые находки этого объёма (`new`, `triaged`, `confirmed`, `in_progress`), которых нет в отчёте, получают `fixed` и событие «не обнаружена при повторном скане» со ссылкой на импорт.
- Находка хранит `scan_scope`, чтобы понимать, к какому объёму она относится.
- Защита от ошибок: упавший импорт ничего не закрывает. Если в отчёте 0 результатов при N > 0 открытых в объёме, автозакрытие **не выполняется**, пока в запросе не передан флаг `confirm_empty=true` (пустой отчёт от сломанного сканера не должен закрыть весь бэклог); в статистику импорта пишется предупреждение.
- Находки `false_positive` и `risk_accepted` автозакрытием не трогаются.

## 5. Владельцы

- **Владелец актива:** `entities.owner_group_id` → группа пользователей (ручная или LDAP — те самые «команды»). Наследуется вниз по дереву, переопределяется на дочернем узле.
- **Правила по путям:** таблица `ownership_rules` (entity_id, маска пути в стиле glob, group_id, приоритет). Действуют на актив и его поддерево. Пример: `app/payments/**` → «Команда платежей».
- **Назначение при импорте:** первое подходящее правило по путям → владелец актива (с наследованием) → пусто («владелец не найден», попадает в очередь AppSec).
- У находки: `assignee_group_id` (обязательно при наличии владельца), `assignee_user_id` (необязательно, вручную).
- Переназначение вручную пишется в историю.

## 6. Сроки (SLA)

- Таблица `sla_policies`: область (entity_id поддерева или глобально), дни по критичности, модификатор для KEV (дни). Ближайшая по дереву политика побеждает.
- Глобальная политика по умолчанию: критичная 15, высокая 30, средняя 90, низкая 180, инфо — без срока; KEV — 7.
- `findings.due_at` вычисляется при создании (от `first_seen`) и при изменении критичности, политики или KEV-статуса.
- Решения «ложное» и «риск принят» снимают срок. Возврат в «Новая» (истёк риск, повторно обнаружена) ставит срок заново от момента возврата.
- Настройка — в UI (раздел «Политики»), не в конфиге.

## 7. История и короткие номера

- `finding_events`: finding_id, тип (`imported`, `status_changed`, `reopened`, `auto_fixed`, `assigned`, `request_created`, `request_decided`, `ai_analysis`, `comment`), actor_type (`user`/`agent`/`system`), actor_id, from_status, to_status, reason, reason_tag, payload JSONB, created_at.
- Короткий номер: `findings.number` — последовательность, отображается как **SV-1482**. Ссылка `/f/SV-1482` ведёт в окно находки (после входа).

## 8. Запросы на решение

`decision_requests`: finding_id, тип (`false_positive` / `risk_accepted`), reason_tag, reason, `expires_at` (только для риска, обязателен), автор, статус (`pending`/`approved`/`rejected`), решивший, комментарий решения, даты.
- Одновременно у находки не более одного активного запроса.
- Готовые причины для «ложного» (`reason_tag`): «Данные не приходят от пользователя», «Тестовый или демо-код», «Уже есть проверка или экранирование», «Код не используется», «Другое» (для «Другое» текст обязателен).
- Истечение риска: ежедневная задача ARQ переводит просроченные `risk_accepted` в `new` с событием.

## 9. Ссылка на строку кода

Нужны репозиторий + коммит + путь + строка. Источники по приоритету: SARIF `versionControlProvenance` → метаданные импорта → настройки актива.
В активе (наследуется): `repo_url`, `repo_type` (`gitlab`/`github`/`gitea`/`bitbucket`), `repo_path_prefix` (подпапка для монорепо).
Шаблоны: GitLab `{repo}/-/blob/{commit}/{path}#L{line}`, GitHub `{repo}/blob/{commit}/{path}#L{line}`, Gitea `{repo}/src/commit/{commit}/{path}#L{line}`, Bitbucket Server `{repo}/browse/{path}?at={commit}#{line}`.
Ссылка ведёт на коммит (стабильная строка); вторая ссылка — «актуальная версия» на основной ветке. Нет репозитория → кнопки нет.
У находки сохраняется `commit_sha` последнего импорта, в котором её видели.

## 10. Экраны

### 10.1. Окно находки (`/f/SV-N`) — для разработчика
Сверху вниз:
1. Критичность, срок («Исправить до 18.10 · осталось 12 дней»), команда, номер.
2. Заголовок простыми словами и объяснение. До ИИ-этапа — название и описание от сканера.
3. «Где»: путь:строка, ссылка «открыть в GitLab», сниппет.
4. «Как исправить»: пример исправления (после ИИ-этапа; до него — рекомендация из SARIF `help`, если есть).
5. Действия: **«Беру в работу»**, **«Ложное срабатывание»** (окно с причинами), **«Нужна помощь AppSec»** (вопрос → очередь AppSec). Подсказка: «Исправили? Находка закроется сама после следующего скана основной ветки».
6. Свёрнутый блок «Подробнее для специалистов»: CWE, сканер, правило, история, похожие, анализ ИИ.
7. Кнопка «Скопировать ссылку».

Для AppSec то же окно показывает дополнительно: «Подтвердить», «Ложное срабатывание» (сразу, без запроса), «Принять риск», переназначение, решение по активному запросу.

### 10.2. Очередь AppSec (`/inbox`)
Вкладки: **Новые** · **Запросы на одобрение** · **Вопросы от команд** · **Просрочены** · **Без владельца** · **Шумные правила**.
Список: чекбокс, критичность, заголовок, сканер · актив · команда, метки (KEV), вердикт ИИ (после ИИ-этапа).
Массовые действия: подтвердить, ложное (с одной причиной), назначить команде.
Горячие клавиши: `J`/`K` — навигация, `C` — подтвердить, `F` — ложное, `A` — назначить, `Enter` — открыть.

### 10.3. «Мои находки» (`/my`) — для разработчика
Находки групп пользователя, по умолчанию: Подтверждена + В работе, сортировка по сроку. Вкладка «Мои запросы» — статус запросов на «ложное».

### 10.4. Настройки актива
Основная ветка, репозиторий (URL, тип, подпапка), команда-владелец, правила по путям, политика SLA — всё с пометкой «унаследовано от …».

### 10.5. Существующая таблица «Находки»
Добавляются: номер, команда, срок, фильтры по команде и «просрочено», ссылка строки на окно находки.

## 11. Отчёт «Шумные правила»

Группировка решённых находок по `(scanner, rule_id)`: всего, доля «ложных», самые частые причины. Порог показа: ≥ 10 решений и ≥ 70% ложных. Цель — подсказать AppSec отключить или настроить правило в сканере.

## 12. Обогащение данными об эксплуатации

- Нормализатор извлекает CVE (`findings.cve`) из rule_id, свойств или текста (регулярка `CVE-\d{4}-\d{4,}`).
- `vuln_intel`: cve (PK), epss, epss_percentile, in_kev, kev_date_added, updated_at. Ежедневная задача ARQ загружает EPSS (FIRST.org) и KEV (CISA). Адреса в settings (`SV_INTEL_EPSS_URL`, `SV_INTEL_KEV_URL`), можно указать внутреннее зеркало; `SV_INTEL_ENABLED`.
- В UI: метка «Эксплуатируется» (KEV), EPSS в процентах, фильтр «Только эксплуатируемые». KEV сокращает срок по SLA.

## 13. ИИ-слой

### 13.1. Подключение (settings)
`SV_AI_PROVIDER` (`ollama` | `openai_compatible`), `SV_AI_BASE_URL`, `SV_AI_API_KEY`, `SV_EMBED_MODEL` (по умолчанию `bge-m3`), `SV_LLM_MODEL` (например `qwen2.5-coder:7b`), `SV_AI_ENABLED`. Без ИИ платформа полностью работает.

### 13.2. Векторная база
- Postgres-образ меняется на `pgvector/pgvector:pg16`; расширение `vector`.
- `finding_embeddings`: finding_id, model, dim, content_hash, embedding, created_at. Индекс HNSW (cosine).
- Канонический текст: сканер, rule_id, CWE, заголовок, сообщение, путь, сниппет. **Секреты маскируются до отправки** (для сканеров секретов — только тип и путь, без значения; плюс общая регулярка по высокоэнтропийным строкам).
- Эмбеддинги считает воркер после импорта. Отдельная задача — backfill и переиндексация при смене модели.
- UI: «Похожие находки» (с решениями команды) в окне находки; поиск по смыслу в таблице находок.
- Поиск похожих всегда фильтруется по правам вызывающего.

### 13.3. Выход для агентов
- `api_tokens`: название, хеш, привязанный пользователь (сервисный аккаунт), срок, последнее использование. Права — через роли, как у людей.
- **MCP-сервер** внутри FastAPI (streamable HTTP, `/mcp`). Инструменты: `search_findings`, `get_finding`, `find_similar`, `list_memories`, `get_stats`, `submit_analysis`.
- `ai_analyses`: finding_id, kind (`summary`/`triage`), verdict (`true_positive`/`false_positive`/`uncertain`), confidence, title_plain, explanation, remediation, similar_ids, memory_ids, agent, model, prompt_version, review_status (`pending`/`accepted`/`rejected`), reviewed_by, created_at.
- «Принять вывод» в UI = обычное действие человека (через запрос или напрямую — по правам), в истории отмечено «по выводу ИИ».
- Данные находок в промптах — недоверенный ввод: явные границы, ИИ не меняет статус сам.

### 13.4. Память команды
- `triage_memories`: область (поддерево активов), условие (scanner, rule_id, CWE, маска пути — любые из них), решение (`false_positive`/`risk_accepted`), обоснование, автор, статус (`suggested`/`approved`/`disabled`), счётчик применений.
- Создаётся AppSec вручную или **предлагается** системой при ≥ 3 одинаковых одобренных решениях по одному правилу в одном поддереве.
- При импорте подходящая находка получает подсказку со ссылкой на память (не решение). Авто-решение по памяти — будущая политика, по умолчанию выключена.

### 13.5. Встроенный ИИ
- `summary`: «простыми словами» заголовок, объяснение и пример исправления для окна разработчика.
- `triage`: встроенный агент-триажёр (воркер ARQ) использует те же инструменты, что и MCP.
- Метрика согласия людей с ИИ на дашборде.

## 14. Этапы

| # | Этап | Состав | Результат |
|---|---|---|---|
| 1 | **Ядро процесса** | Метаданные импорта, основная ветка, автозакрытие, `in_progress`, `finding_events`, номера SV-N, запросы на решение, истечение риска, право `approve`, роль «Разработчик» | Находки закрываются сами, решения обоснованы, история есть |
| 2 | **Владельцы и окна** | owner_group + правила путей, назначение при импорте, ссылка на код, окно находки, очередь AppSec, «Мои находки», массовые действия | Разработчику и AppSec удобно |
| 3 | **Сроки и метрики** | SLA-политики в UI, `due_at`, просрочки, «Шумные правила», метрики на дашборде | Находки не копятся незаметно |
| 4 | **Обогащение** | CVE, EPSS/KEV, модификатор SLA | Приоритет по реальному риску |
| 5 | **Векторная база** | settings ИИ, pgvector, эмбеддинги, маскирование, похожие, поиск по смыслу | Основа для ИИ |
| 6 | **Выход для агентов** | Токены, MCP, `ai_analyses`, блок «Анализ ИИ», вердикт в очереди | Любой агент разбирает находки |
| 7 | **Память команды** | Память, предложения, подсказки при импорте | Меньше повторного труда |
| 8 | **Встроенный ИИ** | Описания простыми словами, встроенный триажёр, метрика согласия | Работает из коробки |

**Позже:** проверки PR/MR, уведомления дайджестом (Telegram/Mattermost/почта), Jira/YouTrack, корреляция между сканерами, чат с базой.

Каждый этап получает свой план реализации; этапы 1–3 можно делать без ИИ.

## 15. Проверка

Для каждого этапа — pytest на API и воркер (в том числе автозакрытие, защита от пустого отчёта, наследование владельца и SLA, права на одобрение) и прогон `scripts/smoke-test.ps1` на примерах из `scripts/samples`, дополненный повторным импортом с «исчезнувшей» находкой. UI — проверка в браузере обеих ролей (bob — разработчик, alice — AppSec).
