# Этап 9. Память команды — спека

Статус: **утверждена 15.11**. План — `docs/superpowers/plans/2026-11-15-stage9-team-memory.md`. Основа — п. 13.4 спеки процесса
(`2026-09-19-triage-workflow-and-ai-design.md`), решения от 15.11 — ниже.

## Зачем

Команда раз за разом принимает одно и то же решение: «`rule X` в `tests/**` — ложное».
Правило команды запоминает это решение и подсказывает его на следующих находках.
Подсказка — **не решение**: статус по-прежнему меняет только человек через запрос решения.

## Принятые решения (15.11)

1. **Подсказка** = метка на находке со ссылкой на правило + кнопка «Запросить по правилу»:
   открывает обычную форму запроса решения, уже заполненную из правила. Одобрение — как сейчас.
2. **Применение**: к новым и переоткрытым находкам при импорте; при утверждении правила — ко всем
   уже открытым подходящим.
3. **Права**: новое право `memory:manage` на поддерево (Инженер ИБ, Администратор). Читают правила
   все, у кого есть `finding:read` на проект.
4. **ИИ**: MCP `list_memories`, правило в `get_finding`, правило в промпте встроенного триажёра (`triage-v3`).

Термин в интерфейсе — **«Правила команды»** (не путать с «Шумными правилами» — это правила сканеров).
В коде и API — `memory` / `triage_memories`.

## Модель данных (миграция 0019)

**`triage_memories`**

| Поле | Смысл |
|---|---|
| `entity_id` | Область: проект и всё его поддерево |
| `scanner`, `rule_id`, `cwe`, `path_glob` | Условие; все заданные поля должны совпасть, **хотя бы одно обязательно** |
| `decision` | `false_positive` / `risk_accepted` |
| `reason_tag`, `reason` | Обоснование (попадает в запрос решения) |
| `status` | `suggested` / `approved` / `disabled` |
| `source` | `manual` / `suggested` |
| `created_by`, `approved_by`, `approved_at` | Кто и когда |

- **`findings.memory_id`** (FK, `SET NULL`) — подсказка. У находки не больше одного правила.
- **`decision_requests.memory_id`** (FK, `SET NULL`) — запрос создан «по правилу»; видно в истории.
- Счётчик применений не хранится: считается по `findings.memory_id`.

## Поведение

**Сопоставление** (`services/memories.py`) — одна функция для импорта и для утверждения правила.
Подходят только правила `approved`, чья область — сам проект находки или его предок.
Маска пути: `*` — внутри каталога, `**` — через каталоги. Если подошло несколько, берётся самое
точное: ближайшая к находке область → больше заданных условий → более раннее.

- **Импорт** (`apply_import`): новым и переоткрытым находкам ставится `memory_id`, в историю —
  событие `memory_hint`. Статус не меняется.
- **Утверждение правила**: `memory_id` получают открытые находки поддерева, подходящие под условие
  (у кого уже стоит более точное правило — не трогаем).
- **Выключение правила**: `memory_id` у его находок сбрасывается и пересчитывается по остальным правилам.
  Уже принятые решения не откатываются.
- **Правка условия или области** утверждённого правила = пересчёт подсказок (сброс + применение).

**Предложения**. После одобрения запроса решения: если в том же проекте набралось **≥ 3** одобренных
решений одного типа по одному `(scanner, rule_id)` и правила с такими же проектом, сканером, `rule_id`
и решением ещё нет (в любом статусе) — создаётся правило `suggested` с обоснованием последнего
решения и самым частым `reason_tag`. Держатель `memory:manage` может поправить (расширить область,
добавить маску пути), утвердить или отклонить. Отклонённое = `disabled`, повторно не предлагается.

**Запрос по правилу**. Кнопка в окне SV-N открывает форму запроса с типом, тегом причины и текстом из
правила; для `risk_accepted` срок вводит человек. Запрос уходит с `memory_id`, право — обычное
`finding:triage`, одобрение — `finding:approve`.

## API и права

- `GET /memories` (фильтры `status`, `entity_id`), `GET /memories/{id}` (с числом открытых находок
  с этой подсказкой), `POST /memories`, `PATCH /memories/{id}` (правка, утвердить, выключить).
- Чтение: правило видно, если его область — в видимом пользователю поддереве **или предок** видимого
  проекта (правило сверху действует на его находки). Изменение — `memory:manage` на область правила;
  чужое → 404.
- `GET /findings`: фильтр `has_memory`; в ответе находки — краткое `memory` (id, решение, обоснование).
- Все изменения правил — в `audit_log` (`record_audit`, сторож покрытия).
- Каталог прав, встроенные роли (`cli.py`), `perm.action` в `ru.json`.

## ИИ

- MCP: `list_memories(project)` — действующие правила для проекта с учётом предков; `get_finding`
  отдаёт правило-подсказку. Права — те же, что у REST.
- Триажёр `triage-v3`: правило-подсказка добавляется в промпт как контекст команды, внутри тех же
  границ недоверенных данных, что и остальное. Вердикт остаётся вердиктом ИИ, статус он не меняет.

## Интерфейс

- Страница **«Правила команды»** (`/memories`): вкладки «Действующие / Предложенные / Выключенные»,
  фильтр по проекту, форма создания и правки, число находок с подсказкой. В сайдбаре — счётчик
  предложенных (только при `memory:manage`).
- Окно SV-N: блок «Правило команды» — решение, обоснование, область, кнопка «Запросить по правилу».
- «Уязвимости»: значок подсказки в строке и фильтр «Есть правило команды».

## Вне этапа

Авто-решение по правилу без человека (будущая политика, по умолчанию выключена); предложения от ИИ;
предпросмотр «сколько находок заденет» до утверждения; срок действия правила; массовый запрос по
правилу сразу на все находки; вкладка правил в настройках проекта.

## Тесты

- pytest: сопоставление (каждое условие, маска пути, выбор самого точного), импорт (новая и
  переоткрытая), утверждение / выключение / правка с пересчётом, порог предложений и отсутствие
  повторов, права на поддерево и видимость правил предков, аудит, MCP, промпт `triage-v3`.
- e2e: один сценарий — создать и утвердить правило → подсказка в окне SV-N → запрос по правилу → одобрение.

## Порядок работы

Две сессии: **бэкенд** (модель, сервис, API, импорт, предложения, MCP, промпт, pytest) → записка
`docs/stage9-handoff.md` → **фронтенд** (страница, блок в окне, фильтр, e2e). Ревью `sv-reviewer` —
одно, по диффу этапа.
