# Этап 3 «Сроки и метрики» — спека

Основа — спека процесса `2026-09-19-triage-workflow-and-ai-design.md` (§6 SLA, §11 «Шумные правила»). Здесь — решения этапа и что изменилось после ревью дизайна.

## Решения

| Вопрос | Решение |
|---|---|
| К чему привязана политика SLA | **Только к дереву**: `entities.sla_policy_id`, наследуется вниз, ближайшая побеждает; иначе политика по умолчанию |
| Теги | Есть в этапе, но **только для фильтров и метрик**, на сроки не влияют. Наследуются вниз |
| KEV-модификатор, сроки по тегам | Не входит (этап 4 / потом) |
| Дашборд | Один generic-эндпоинт агрегатов; набор виджетов — JSON-конфиги в коде фронтенда. Конструктор виджетов — бэклог |
| Старые находки при миграции | Не важны: простой backfill, без восстановления из истории |

## Данные

- **`sla_policies`**: `name` (уникальное), `days_critical`, `days_high`, `days_medium`, `days_low`, `days_info` (int, NULL = без срока, иначе 1..3650), `is_default` (bool; частичный уникальный индекс — ровно одна по умолчанию). Миграция создаёт «Стандартная» 15/30/90/180/NULL, `is_default=true`.
- **`entities`**: `sla_policy_id` (FK, NULL = наследовать, `ON DELETE RESTRICT`), `tags` (`text[]`, default `{}`, GIN-индекс).
- **`findings`**: `sla_start_at`, `due_at`, `resolved_at` (timestamptz, NULL), индекс по `due_at`.
- Миграция: простой backfill — `sla_start_at = first_seen`, `due_at` по политике по умолчанию, `resolved_at = last_seen` для закрытых. Точность для уже существующих находок не важна (решено пользователем).

## Правила срока

- Открытые статусы: `new`, `triaged`, `confirmed`, `in_progress`. Закрытые: `fixed`, `false_positive`, `risk_accepted`.
- `due_at = sla_start_at + days[severity]` эффективной политики; `days` NULL → `due_at` NULL.
- **Просрочена** = статус открытый и `due_at < now()`. Отдельного статуса и cron нет.
- **Единая точка смены статуса** (найдено на ревью: сейчас статус меняется в 6 местах — PATCH, bulk, одобрение решения, автозакрытие и переоткрытие в импорте, истечение риска). Новый сервис `services/finding_state.py`:
  - `set_status(finding, new_status)`: в закрытый → `resolved_at = now`; из закрытого в открытый → `resolved_at = NULL`, `sla_start_at = now`, пересчёт `due_at`. Все 6 мест переводятся на него (запись события остаётся у вызывающего).
  - `recompute_due(db, *, entity_ids=None)`: пересчёт `due_at` **только открытых** находок по эффективной политике; закрытые не трогаем — по ним считается «закрыто в срок».
- Пересчёт вызывается: при создании находки, смене severity, смене `sla_policy_id` у проекта (поддерево), изменении дней политики (все проекты, где она эффективна), смене default.
- Эффективная политика и теги поддерева — через общий резолвер наследования (переиспользовать подход `entity_settings.py`). Поддерево по `path_cache` — **без LIKE** (в именах бывают `_`/`%`): `path_cache = p OR left(path_cache, len(p)+1) = p || '/'`.

## Теги

- Формат: `^[a-z0-9][a-z0-9_.-]*(:[a-z0-9_./-]+)?$`, до 64 символов, до 20 на проект, приводятся к нижнему регистру, дубли убираются. Ошибка формата — 422 с понятным текстом.
- Эффективные теги проекта = свои ∪ всех предков. Фильтр `tag=` у находок и метрик матчит по эффективным тегам.
- `GET /tags` — существующие значения для подсказок.

## API

- `GET/POST/PATCH/DELETE /sla-policies` — права `sla:read` / `sla:manage` (в каталог прав и встроенные роли: AppSec — manage, разработчик — read). Удаление назначенной или default-политики — 409. Смена default — `PATCH {is_default: true}` снимает флаг со старой в той же транзакции.
- Настройки проекта: `sla_policy_id`, `tags` на запись; на чтение — эффективная политика с пометкой «унаследовано от <path>» и эффективные теги с источником.
- `GET /findings`: фильтры `overdue=true`, `tag=`; сортировка `due_at` (NULL в конце); в ответе `due_at`, `resolved_at`.
- `GET /findings/noisy-rules?min_decided=10&min_fp_ratio=0.7`: по `(scanner, rule_id)` — решено (статусы `confirmed`, `in_progress`, `fixed`, `false_positive`, `risk_accepted`), из них ложных, доля, топ-3 `reason_tag`. Право `finding:read`.
- `POST /metrics/aggregate` (`finding:read`), тело = JSON виджета:
  - `metric`: `count` | `opened` (по `first_seen`) | `resolved` (по `resolved_at`) | `overdue` | `sla_ratio` | `mttr_days`;
  - `group_by`: `none` | `severity` | `scanner` | `team` (`assignee_group_id`) | `entity` | `week`;
  - `period`: `7d` | `30d` | `90d` | `365d`; `filters`: `severity[]`, `scanner`, `entity_id` (с поддеревом), `tag`.
  - `sla_ratio` = доля открытых с `due_at` не просроченных; `mttr_days` = среднее `resolved_at - first_seen` для `fixed` за период. Находки без `due_at` в `sla_ratio` не участвуют.
  - Только белые списки значений (без сырого SQL из запроса), не более 50 групп, `week` — по `date_trunc('week')` в UTC.

## Интерфейс (вторая сессия)

- Раздел «Политики SLA»: таблица, создание и редактирование, отметка «по умолчанию».
- Проект: выбор политики («унаследовано от …»), редактор тегов с подсказками.
- Уязвимости: колонка «Срок» («осталось N дн.» / «просрочена на N дн.» / «—»), фильтры «Просрочено» и «Тег», сортировка по сроку.
- Окно уязвимости: «Исправить до ДД.ММ · осталось N дней».
- Очередь AppSec: вкладки «Просрочены» и «Шумные правила».
- Дашборд: плитки (просрочено, доля в SLA, MTTR по критичности), график «появилось / закрыто» по неделям.
- Все строки — в `ru.json`; срок — цвет + текст (не только цвет).

## Не входит

Сроки по тегам, KEV/EPSS, права на поддерево, конструктор виджетов, справочник ключей тегов, уведомления о приближении срока.

## Тесты

- `set_status`: все переходы (в закрытый, переоткрытие — новый отсчёт, закрытый→закрытый не трогает `sla_start_at`).
- Наследование политики: своя / от предка / default; смена политики на узле пересчитывает поддерево, но не находки с собственной политикой ниже и не закрытые.
- Severity без срока → `due_at` NULL, не просрочена.
- Теги: валидация, наследование, фильтр; имя проекта с `_` не цепляет соседей.
- `/sla-policies`: права, 409 на удаление, единственность default.
- `noisy-rules`: пороги, топ причин.
- `metrics/aggregate`: каждая метрика на маленьком наборе, неизвестный `group_by` → 422.
- Смоук импорта + повторный импорт с исчезнувшей находкой → `resolved_at` выставлен.
